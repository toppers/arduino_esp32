# dev ツリーとの同期監査（2026-09-20）

`ports/m5stack_*/runtime/` は開発ツリー `fmp3_esp_idf_dev` の `esp/` `m5/`
`fmp3/` からの**複製**である。複製が古くなると、向こうで直った欠陥がこちらに
残る。2026-09-20 に実機で出た「Wi-Fi 切断後に全タスクが 296 秒止まる」
（[`xtensa-timer-starvation.md`](xtensa-timer-starvation.md)）がまさにそれ
だったため、同日ツリー全体を洗った。

## 結果

| | Xtensa（S3/LX6） | RISC-V（C6/C5/P4） |
|---|---|---|
| 対応がついたファイル | 214 | 248 |
| コード同一（コメントを除く） | 146 | **240** |
| コードが違う | 68 | 8 |

**取り残しは Xtensa 側に集中している。** 確定したのは 3 件で、いずれも同日
直した:

| # | 件 | dev で直った日 | 直したブランチ |
|---|---|---|---|
| A-1 | `esp_shim_time_us()` が 32bit HRT を返し **71.6 分で時刻が巻き戻る** | 2026-07-27 | `fix/xtensa-hrt-drift` |
| A-2 | `target_hrt_raise_event()` が `ccount+1` を 1 回置くだけで取りこぼす | 2026-07-28 | 同上 |
| A-3 | タイマ待ちの `TMAX_RELTIM` 頭打ち／ms→us の 32bit 折り返し | 2026-08-14 | `fix/xtensa-shim-timer-clamp` |

**A-1・A-2 は ESP32-S3 だけの取り残しだった**——同じこのリポジトリの中で、
LX6 の `target_timer.h` には両方入っていて S3 のそれには入っていなかった。
複製は板ごとに別のタイミングで取られており、古さも板ごとに違う。

## A-1 の実機実証（2026-09-20、M5CoreS3）

`esp_shim_time_us()` を 30 秒ごとに 64bit のまま印字する像を焼いて **85 分**
走らせた（`.steering/20260920-tree-drift/raw/s3-hrt-soak.log`、171 サンプル）:

- **64bit 値は 171 サンプルすべてで単調増加**（刻みは 30.005〜30.011 秒）。
- **72.0 分の時点で 2^32us を跨いだ**（n=145 で `hi=0 -> 1`）。
- 逆行の検出カウンタは最後まで **0**、`unexpected=0`。

**旧コードなら、ここで下位 32bit が 0 付近へ戻り上位は 0 のままだった**
（32bit をゼロ拡張して返していたため）。跨いだ先で `hi=1` が出ていることが、
64bit 累積器を実際に使っている一次証拠である。

## 手順（再現できる形）

検出器と採取は開発ツリー側の `.steering/20260920-tree-drift/` に置いた。

1. 名前で対応づけて内容ハッシュ（`raw/codediff.py`）
2. **コメントを除いたコード**だけで比較（移植の適応はコメント差として大量に
   出るので、生の diff では読めない）
3. **前処理の文脈で絞る**（`#if TOPPERS_ESP32C6` / `#ifdef M5_A4_HANGDIAG` /
   `TNUM_PRCID>=2` / `M5_PSRAM` の中は、この移植では正当に無い。`raw/relevant.py`）

補助として「dev にある日付つきのバグ修正記述が複製に無い」も見たが、
**偽陽性（書き方を変えただけ）も偽陰性（日付を書かずに直した修正）も出る**。
A-3 はこれで、A-1 はコード比較の側で見つかった。⇒ **積集合ではなく和集合を読む。**
